# 玩法架构 v0.2

## 目标

第一阶段不做复杂关系、导演、剧情生成。只验证：建设、生产、物流、劳动力分配、灵气布局、修炼成长是否本身好玩。

## 当前核心循环

1. 仓库里存在真实资源，而不是只有一个全局数字。
2. 玩家放置建筑后先生成工地。
3. `LogisticsManager` 根据工地需求创建 Haul Job。
4. 弟子去仓库取材料，实际携带到工地。
5. 材料齐全后产生 Build Job，弟子施工完成建筑。
6. 灵田完成工作后把产物放进本地 Output 容器。
7. 弟子把产物搬回仓库。
8. 工坊有 Input 容器，物流会先把配方材料搬进去，再产生 Craft Job。
9. 玩家通过工作优先级 UI 决定每个弟子更偏向搬运、建造、种植、制造还是修炼。

## 数据层

建筑已迁移到 `BuildingDefinition : ScriptableObject`。

一个建筑定义负责描述：

- 建造成本与施工工作量
- 基础视觉形状、尺寸、颜色
- Producer / Processor / Cultivation / QiSource / Storage 行为
- 工作类型、周期、工作量
- 输入配方、输出配方、缓存容量
- 仓库容量
- 聚灵强度与半径

`Tools > ShanMen > Create Prototype Scene` 会创建/更新默认建筑 Definition 资产，因此新增内容不需要继续往 `BuildController` 里堆 if/switch。

## Job 原则

当前 Job 类型：Haul 搬运、Build 建造、Farm 种植、Craft 制造、Cultivate 修炼。

优先级为 0 时该弟子不会主动领取对应工作；1-5 越高越优先。JobBoard 会在同优先级下考虑距离。

## 系统原则

- 所有长期行为尽量转成 Job，不把 NPC 写死在建筑逻辑里。
- 资源必须存在于具体容器，生产/消费尽量通过物流连接。
- 建筑内容由 ScriptableObject 数据定义，运行时逻辑保持通用。
- 地图场按 Dirty Cache 更新，避免每帧全地图重算。
- 角色属性只有在影响玩家决策时才增加。
- 随机事件只改变经营条件，不负责替玩家讲故事。
