# 玩法架构 v0.3

## 目标

第一阶段不做复杂关系、导演、剧情生成。只验证：建设、生产、物流、劳动力分配、生活需求、灵气布局、修炼成长是否本身好玩。

## 当前核心循环

1. 仓库里存在真实资源，而不是只有一个全局数字。
2. 玩家放置建筑后先生成工地。
3. `LogisticsManager` 根据工地需求创建 Haul Job。
4. 弟子去仓库取材料，实际携带到工地。
5. 材料齐全后产生 Build Job，弟子施工完成建筑。
6. 玩家可取消工地；已送达材料转成地面返料堆，再通过物流搬回仓库。
7. 灵田完成工作后把产物放进本地 Output 容器。
8. 弟子把产物搬回仓库。
9. 工坊有 Input 容器，物流会先把配方材料搬进去，再产生 Craft Job。
10. 仓库可过滤资源并设置物流优先级；高优先仓可从低优先仓调货。
11. 弟子持续消耗饱食和体力；饥饿会寻找食物，疲劳会寻找空床，需求过低会降低工作效率。
12. 玩家通过工作优先级 UI 决定每个弟子更偏向搬运、建造、种植、制造还是修炼。

## 数据层

建筑使用 `BuildingDefinition : ScriptableObject`。

一个建筑定义负责描述：

- 建造成本与施工工作量
- 基础视觉形状、尺寸、颜色
- Producer / Processor / Cultivation / QiSource / Storage / Rest 行为
- 工作类型、周期、工作量
- 输入配方、输出配方、缓存容量
- 仓库容量
- 聚灵强度与半径

`Tools > ShanMen > Create Prototype Scene` 会创建/更新默认建筑 Definition 资产，因此新增内容不需要继续往 `BuildController` 里堆 if/switch。

## 物流原则

- 资源必须存在于具体 `ResourceContainer`。
- Input 与 Construction 容器提出明确需求。
- Output 容器主动向仓库出货。
- Stockpile 仓库通过过滤决定接收哪些资源。
- 仓库优先级 0-5；高优先仓优先接货，并可从低优先仓抽调现有库存。
- 取消工地不直接修改总账，而是生成可搬运返料，因此距离和劳动力仍然有成本。

## 弟子需求

`CultivatorNeeds` 当前只保留两个真正影响经营的需求：

- 饱食：通过真实消耗 Food 恢复。
- 体力：通过占用 `RestSpot` 床位恢复。

两者过低都会降低移动和工作效率。暂时不加入心情、社交、娱乐等系统，除非后续证明它们能增加有意义的经营决策。

## Job 原则

当前 Job 类型：Haul 搬运、Build 建造、Farm 种植、Craft 制造、Cultivate 修炼。

优先级为 0 时该弟子不会主动领取对应工作；1-5 越高越优先。JobBoard 会在同优先级下考虑距离。

吃饭和休息属于个人生存行为，目前不占玩家工作优先级列；弟子只在空闲于正式 Job 之间时处理需求，从而避免半路丢下正在搬运的资源。

## UI 原则

当前三块运行时 UI 都服务于经营决策：

- 底部建筑工具栏：建筑、快捷键、成本、当前选择。
- 左上仓库面板：仓库物流优先级和资源过滤。
- 右上弟子面板：当前工作、饱食/体力、工作优先级。

暂时不做装饰型 UI 和复杂动效。

## 系统原则

- 所有长期生产行为尽量转成 Job，不把 NPC 写死在建筑逻辑里。
- 资源必须存在于具体容器，生产/消费尽量通过物流连接。
- 建筑内容由 ScriptableObject 数据定义，运行时逻辑保持通用。
- 地图场按 Dirty Cache 更新，避免每帧全地图重算。
- 角色属性只有在影响玩家决策时才增加。
- 随机事件只改变经营条件，不负责替玩家讲故事。

## 下一批实现

优先继续增加“经营上的选择”，而不是内容数量：

- 地面自然资源与采集点：木材、石料、灵草来源不再只有初始仓库。
- 多格建筑与道路/移动成本，让空间布局真正影响物流效率。
- 五行环境场与建筑相生相克，让修炼区、生产区产生布局取舍。
- 建筑详情/产能瓶颈 UI，明确告诉玩家哪里卡住。
- 突破准备界面与风险/收益选择。
- 探索地图与资源点占领，把高级资源获取接回经营循环。
- 存档系统。
- 微信小游戏/Web 性能档位。
